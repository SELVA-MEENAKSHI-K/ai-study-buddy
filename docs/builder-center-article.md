# AI Study Buddy: a friendly agent for learning computer science

College students learning programming often hit a small but frustrating wall: the textbook definition makes sense on paper, but the idea still will not click. AI Study Buddy is a learning companion designed for that moment. It helps students ask questions about programming and computer science, understand difficult ideas in plain language, and find a next step when they are stuck.

The project is for students who want approachable explanations without giving up on understanding. A student can ask about recursion, data structures, SQL, or another technical topic and choose a response style that fits their goal. Beginner mode favors simple wording and a practical example. Exam prep mode organizes a response into a definition and concise key points. Practical mode teaches through a small example and an exercise. Students can switch modes at any time, so the same study space works for a first introduction or a quick review.

The central design choice is to make the next action obvious. The page opens with example questions, not an empty chat window. A short selector gives students control over the explanation style, and the recent-question list makes it easy to revisit what they asked during the current browser session. The interface does not ask for a student’s name, school, or account. Recent chat context stays in the current browser tab, and the backend receives only the question, selected learning mode, and a small bounded conversation history needed to answer coherently.

The signature feature is **Explain it another way**. Sometimes a technically correct explanation still does not help. Instead of making the student retype the question, the button reuses the original topic and requests three fresh angles: simpler wording, a practical example, and a real-world analogy. That gives a learner a low-effort way to say, “I’m still working on it,” and keeps the conversation focused on understanding rather than on prompt writing.

The application uses a React and Vite frontend with a Python backend. It has two model routes: a Strands Agents SDK route to Amazon Bedrock using Nova Lite, and a local Ollama route using Qwen 2.5 3B. I used the local Ollama route for this no-cloud-inference-cost demo; the prompt and response ran on my computer, and I did not send an inference request to Bedrock. The Bedrock route remains available through environment settings and uses the standard AWS credential chain. Its agent also has a curated learning-resource tool that returns links from known documentation and course sources. The local Ollama route answers from its model knowledge and does not call that Bedrock tool, so I should not present its responses as sourced research.

The backend validates message size and learning mode, limits the amount of context passed to the agent, applies a response timeout, and returns readable error messages without exposing internal exception details. The interface shows a loading state, retains the question after an error, and offers a retry. This matters for a student-facing tool: a failed request should be recoverable, and confusing technical details should not be the student’s problem.

The feature evaluation is designed around observable behaviors rather than a claim that the model is always right. The predefined cases check that the alternate-explanation request reuses the original question, that the request flag reaches the backend agent, that a successful response appears, and that a failed request offers a retry. Human review should additionally check three sample subjects—recursion, SQL joins, and binary search—for simpler wording, a genuinely different example, a useful analogy, and no invented citations. Automated frontend and API tests are included to exercise the request flow with mocked responses, so they can be run without spending on model calls. These checks evaluate product behavior and the shape of the alternate explanation; they do not establish educational effectiveness or factual accuracy across all topics. No real-user feedback is claimed here. A useful next evaluation would invite a small group of students to try the feature, ask whether the second explanation helped, and record their responses only with consent.

For this demo I installed Ollama and downloaded the 1.9 GB Qwen 2.5 3B model, then ran the app locally with Node.js and Python. The local route made no Bedrock inference calls and incurred no model API charge; the model download uses disk space and internet bandwidth, and generation uses the computer's resources. The project also includes a Bedrock route, but I have not verified a live Bedrock request or used an AWS runtime service in this demo. In the article, I will disclose that distinction and name the AWS services actually used rather than imply Bedrock powered the local demo. The app is not deployed, and this draft has not been published to AWS Builder Center.
